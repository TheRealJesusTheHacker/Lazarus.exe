# CI dependency pins for the Windows release build.
#
# HASH LOCK (2026-10-25, --require-hashes fleet rollout): installs
# use the committed lock beside this file --
#   pip install --require-hashes -r packaging/requirements-ci.lock.txt
# The lock carries the full resolved set (direct + transitive)
# with a sha256 for every artifact, and pip fails loudly on any
# mismatch. This file remains the human-edited pin list; a pin
# bump here is not landed until the lock is regenerated (the
# procedure is in the lock's header).
#
# EXACT versions on purpose: the release pipeline must build with
# the same libraries every time, never with whatever happens to be
# newest on release day. These are the same pins the Argus, Charon,
# and Beerus release pipelines use (verified on PyPI 2026-10-19);
# bump deliberately, in review, never by loosening a pin.
#
# Lazarus imports no pywin32 (its Windows seams drive manage-bde,
# PowerShell, and schtasks through subprocess argv lists), so the
# pywin32 pins Charon needs are not here — the list is what this
# build actually uses, nothing more.
#
# 2026-10-23 (Fleet Sweep #4): setuptools is pinned at 83.0.0, not
# the fleet's earlier 80.10.2 — 80.10.2 carries PYSEC-2026-3447
# (an sdist MANIFEST.in glob flaw). The flaw is build-time only,
# but a pinned build tool with a known vulnerability does not
# stay pinned.
PySide6==6.12.0
pyinstaller==6.22.3
pyinstaller-hooks-contrib==2026.8
pefile==2024.8.26
altgraph==0.17.5
pywin32-ctypes==0.2.3
packaging==25.0
# 2026-10-24 (Fleet Sweep #5 close-out): setuptools is pinned at
# 84.1.0, not 83.0.0 — 83.0.0 carries GHSA-xmj3-9gf7-h52w (a Windows
# path escape via namespace_packages.txt during legacy wheel
# installation, fixed in 84.1.0). Build-time only, the same rule as
# Sweep #4: a pinned build tool with a known vulnerability does not
# stay pinned.
setuptools==84.1.0
pytest==9.1.1
